# ADR-001: MCP アーキテクチャ決定

- **ステータス:** 承認済み
- **日付:** 2026-04-09
- **決定者:** ARCH

## コンテキスト

国会議事録を検索・要約するツールを MCP サーバーとして提供する。
初期版は「画面・DB なし、MCP 単体で価値を出す」方針。

## 決定事項

### 1. Transport: stdio を採用する

**理由:**
- Claude Desktop との統合に最も適合する（公式推奨方式）
- HTTP サーバーを立てる必要がなく、初期構成を最小化できる
- 将来的に HTTP transport への切り替えも `@modelcontextprotocol/sdk` の変更のみで対応可能

**却下した選択肢:** HTTP/SSE transport（初期版には過剰）

### 2. ツールを 4 つに限定する

検索・取得・要約という機能を 4 ツールに分離する:
- `search_speeches`: 発言検索（軽量、キャッシュ 1 日）
- `get_meeting`: 会議録取得（重め、キャッシュ 7 日）
- `summarize_speeches`: 検索結果の要約（LLM 使用）
- `summarize_meeting`: 会議録全体の要約（LLM 使用）

**理由:** MCP クライアント（LLM）がツールを選択する際の認知負荷を下げるため、
ツール数を最小化し、各ツールの責務を明確にする。

### 3. DB なし・メモリキャッシュのみ

**理由:**
- 初期版の目標は「まず使えること」（要件定義 §20）
- 国会 API のデータは変更されない（会議録は確定データ）ため長期キャッシュが有効
- プロセス再起動でキャッシュが消えても業務上は許容できる

**将来対応:** Redis や SQLite への移行は `cache.ts` の実装を差し替えるだけで対応可能なインターフェースを設計する。

### 4. 要約は段階要約（チャンク → 部分要約 → 最終統合）

**理由:**
- 会議録全体を 1 回の LLM 呼び出しに渡すとコストと精度の両面でリスクがある
- チャンク分割により、大量発言も安定して処理できる
- 要件定義 §12（コスト要件）の必須事項

### 5. 要約モデルは Anthropic Claude API（claude-3-5-haiku 優先）

**理由:**
- コスト効率が高い（haiku は高速・低コスト）
- final 統合のみ必要に応じて上位モデルに切り替える構成にする
- API キーは環境変数 `ANTHROPIC_API_KEY` で管理

## 結果

- `src/` 以下の 4 レイヤー構成（server → tools → services → external）
- 疎結合設計により将来の Web 画面・DB 追加が容易
- `config/index.ts` で環境変数を一元管理し、`process.env` 直接参照を排除
